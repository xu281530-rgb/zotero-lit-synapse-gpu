## 一、结论

**上轮列出的三个缺陷已在本次回归测试中修复；原有31项正常行为仍然通过。对于单一文库、本地个人使用，本次检查未发现需要阻止开始使用的已确认缺陷，可以进入真实使用验收。**

**仍存在1处已确认的条件性缺陷：底层 MinerU 的解析任务和结构化缓存没有按文库隔离。跨文库出现相同附件 key 时，可能复用另一份文献的解析结果。** 本次用两个场景复现，不能把它们夸大成两个无关的新 bug。

因此，判断分为两层：
- 单一文库、本地个人使用：具备可用基础，可以开始实际使用验证；没有必要继续全项目重构。
- 宣称多文库高精度解析稳定、面向所有使用场景的正式版：暂不无条件通过。先修复下面 C1，并完成真实 Zotero 中的核心流程验收。

“没有在真实 Zotero 中验收”是证据边界，不是额外发现的 bug；“可以开始使用”也不是“已经证明所有功能都稳定”。

## 三、上轮三项缺陷的关闭依据

### B1：旧 socket 异步关闭回调干扰新监听——回归通过

主脚本关键位置：
- `56462–56493`：`stop()` 先取出当前 socket 并清空状态，无论布尔标志是否为 false 都执行实际清理。
- `56559–56570`：拒绝旧 socket 或已停止状态下迟到的连接。
- `56852–56858`：关闭回调核对 socket 身份，旧回调不再关闭新服务。

测试结果：启动旧端口、停止、启动新端口、触发旧关闭回调后，新服务仍报告运行且可被 `stop()` 关闭。两次快速重绑、乱序旧回调、绑定失败后再启动、重复停止、活动连接清理也通过。

Mozilla 接口明确说明 `close()` 的通知为异步，模拟时序有宿主约定依据[1]。测试仍不是实测操作系统端口。

### B2：阅读器翻译缓存跨文库混用——回归通过

阅读器关键位置：
- `194–213`：统一身份采用 `libraryID:key`；目录为 `mineru/reader/<libraryID>/<key>`。
- `566–644`：内存/磁盘读取及旧缓存迁移核对归属。
- `692–721`：写入队列和缓存通知采用同一身份。
- `1539–1570`：全文翻译任务的文档快照与术语编辑使用完整身份。
- `translation-task.js:234、245、254、262、359`：界面选择值和保存调用已同步。

测试结果：不同文库相同 key 的目录、内存缓存、磁盘保存和术语编辑相互独立；模拟清空内存后再次读取仍隔离。带明确归属的旧缓存可迁移；缺少 libraryID 的旧缓存只有元数据匹配且数据库归属唯一时才迁移；归属有歧义时不复制，也不删除旧文件。

**这一层的旧问题可以关闭。下面 C1 位于它依赖的底层 MinerU 服务，不能将两者混为“阅读器修复无效”。**

### B3：索引忙碌时丢弃群组文献新增事件——回归通过

主脚本关键位置：
- `60891–60924`：不再因为 `isAutoIndexing` 为 true 就丢弃普通新增/修改事件。
- `60553–60591`：当前批次完成后继续处理期间到达的任务。
- `61042–61060`：周期构建结束后排空新增队列。

测试不仅验证“能入队”，还让一个模拟的异步构建保持未完成，在此期间插入群组文献；完成后执行新排定的回调，实际对群组库调用 `buildIndex`。普通增量构建和周期个人库构建两条路径均通过。服务未就绪、返回 busy、暂停/恢复、重试耗尽时保留任务等检查也通过。

## 四、剩余已确认缺陷 C1：MinerU 底层解析任务和结构化缓存仍按 key 区分

### 4.1 根因与范围

主脚本：
- `3968–3969`：`inFlight` 用于解析任务去重。
- `4041–4043`：`getAttachmentDir(attachmentKey)` 的路径只有 key，没有 libraryID。
- `4474–4489`：正在进行的任务按 `attachment.key` 查找、写入和删除。
- `5284–5318`：`readStructuredCache(attachmentKey, config, stat)` 检查文件大小、修改时间、配置等，但不校验请求文库与 `meta.libraryID`。
- `4373–4397`：取得结构化缓存后，必要时据其内容重新同步 Markdown 附件。

Zotero 的条目唯一性约束是 `(libraryID, key)`，不是 key 全局唯一[2]。因此，不同文库相同 key 是宿主数据模型允许的条件。本报告没有测量它的出现频率，也不声称普通使用总会遇到。

### 4.2 场景 C1a：同时解析不同文库的同 key 附件

合成输入：
- A：`libraryID=1, key=SAMEKEY1`，PDF路径 `/pdf/a.pdf`。
- B：`libraryID=7, key=SAMEKEY1`，PDF路径 `/pdf/b.pdf`。
- A、B大小和修改时间不同，不依赖磁盘指纹碰撞。
- A的解析尚未返回时发起B的强制解析；外部解析响应被控制，以确定性实现这个异步顺序。

实际输出：

```json
{
  "libraries": [1, 7],
  "sameAttachmentKey": "SAMEKEY1",
  "differentFileStats": true,
  "parseCalls": ["/pdf/a.pdf"],
  "library7Received": "Paper A evidence.",
  "library7OwnPDFParsed": false
}
```

B命中A的 `inFlight`，直接取得A的解析结果。测试中只创建了A所属文库的 Markdown 附件，B自己的PDF根本没有被交给模拟解析客户端。

对照：同一附件的重复请求只解析一次，这是正确行为；不同 key 的两份附件分别得到自己的解析结果。异常集中在“不同文库、相同 key”的身份混淆。

### 4.3 场景 C1b：串行解析后，结构化缓存跨文库覆盖与错误复用

先解析A，再解析B，二者写入同一个目录：

```text
/test-data/zotero-lit-synapse/mineru/SAMEKEY1
```

B写入后，该目录的元数据归属为文库7，A的结构化缓存已被覆盖。进一步让A、B的文件大小和修改时间相同，再读取A，包内原始缓存读取逻辑接受B的缓存，随后原始附件同步逻辑把B的 Markdown 导入到A的父条目。

实际输出：

```json
{
  "cachedOwnerAfterB": 7,
  "statCollisionAddedForDiskReuse": true,
  "library1ReadAfterB": "Paper B different evidence text.",
  "wrongMarkdownImportedToLibrary1": true
}
```

**覆盖共享缓存仅需要跨文库同 key；把另一文库缓存当作“新鲜”结果复用还需要相应大小、时间和配置条件。** 两个条件必须区分。这里的导入发生于内存模拟接口，没有修改用户的真实文库，也没有证明原始 PDF 本身被更改。

### 4.4 这是新回归吗？

不是。C1a、C1b在旧安装包上同样复现。它是上一轮未检查完整的相关底层问题，而不是这轮修复产生的故障。上一轮确认到阅读器缓存，未覆盖到下面的 MinerU 任务与结构化缓存隔离；本轮补齐了这一证据。

### 4.5 处理优先级

- 单一文库使用：不满足跨文库触发条件，此问题不是该范围内的发布阻断项。
- 同时处理个人库和群组库：应修复；由于影响解析结果与文献的对应关系，不能当作纯界面优化。
- 暂时串行执行：可避免C1a，但不能消除C1b，不应称为完整解决方案。

最小修复应同时覆盖：
1. 解析任务 `inFlight` 改为完整文库身份，不只改阅读器缓存。
2. 结构化缓存、元数据与相关临时文件路径按文库隔离；同步更新调用者。
3. 读取缓存时验证附件 key 与文库归属。旧缓存只在归属明确时迁移，歧义缓存不自动套用到当前文库。

不需要为此重新设计整个插件。对应验收就用同 key、不同文库的并发与串行两个场景。

## 五、是否可用：按实际使用范围作决定

| 使用范围 | 判断 |
|---|---|
| 只在一个文库内使用，本地个人流程 | 可以开始实际使用验证；本轮没有确认该范围内的阻断项 |
| 修改端口、停止后重新启动 | 上轮代码缺陷已修；仍需在真实宿主验证端口确实关闭 |
| 阅读器翻译缓存、多文库术语编辑 | 对应隔离修复通过，不再按旧 B2 判断不通过 |
| 索引运行时到达的群组文献变更 | 本轮队列回归通过，不再按旧 B3 判断丢事件 |
| 多文库 MinerU 高精度解析 | 尚有C1，不能无条件称为可靠 |
| 对全部功能与环境给出稳定正式版承诺 | 证据不足；修复适用问题，并验收声明范围内的真实流程 |

完成当前版本所需的宿主验收可以收敛为：

1. 在包内声明支持的 Zotero 9.0.x 中安装、重启；启用服务、改端口、停止，确认服务状态与实际连接一致。
2. 用少量已有备份的文献走通索引、检索、PDF阅读及一次真实翻译，并检查结果属于正确文献。
3. 使用写入/Wiki功能时，补上实际使用的流程；例如拒绝确认不写入、批准只写一次。未测试的可选功能不要宣称已经验收。
4. 多文库作为支持范围时修复C1，执行同 key 并发和串行回归。单一文库使用者不必为不使用的多文库场景无限等待。

**达到声明范围内的验收标准即可结束当前版本，而不是以“AI再也提不出任何建议”为终点。**
