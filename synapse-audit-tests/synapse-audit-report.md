# Zotero LitSynapse 3.1.0：缺陷与可用性审查

审查日期：2026-09-05  
审查对象：本次上传的 `zotero-lit-synapse.xpi`，不是此前其他安装包。  
SHA-256：`55beb39978f90f434885f9eb26eab5282fad2041bf433877fcc49fa8c10a970e`  
清单声明的 Zotero 兼容范围：`9.0` 至 `9.0.*`。

## 一、结论

**至少存在 3 处本次已通过原始代码模拟测试复现的实质缺陷。当前版本具有受控试用基础，但不建议直接按“稳定正式版”验收。**

这不是“AI 还能想到优化建议，所以永远不能发布”的判断。三项问题都有具体输入或事件顺序、原始代码位置和可重复的异常结果。另一方面，31 项正常行为与保护检查通过，不能把这三项局部缺陷扩大为“整个插件不能用”。

用途判断：

| 使用范围 | 本次判断 |
|---|---|
| Zotero 9.0.x，个人库，小范围只读检索，固定本地服务配置 | 可以进入受控试用；尚不是宿主端到端验收通过 |
| 运行时更换服务端口、切换监听范围、反复重启服务 | 先修复 B1；当前关闭状态不可靠 |
| 多文库阅读翻译 | 存在 B2 条件性缓存混用，需要修复或限制使用范围 |
| 群组库自动增量索引 | 存在 B3 丢事件问题，不能只依赖自动更新 |
| 面向普通用户、默认认为各宣称功能均稳定的正式发布 | 本次暂不通过，应修复相关缺陷并完成真实 Zotero 验收 |

这里的“受控试用”指：先备份，在少量非关键文献上验证，保持固定本地配置，不直接把未经验证的批量写入交给自动流程；不是认证所有功能正常。

## 二、方法和边界

1. 解压安装包，检查 manifest、默认偏好、启动/退出与资源组织；阅读关键模块和调用路径。
2. 对安装包内全部 7 个 JavaScript 文件运行 `node --check`，全部通过。语法通过不等于能在 Zotero 中成功启动。
3. 使用 Node.js v22.16.0 执行安装包提取的原始函数/类，模拟 Zotero、Mozilla socket、文件系统和对话框等外部依赖。
4. 运行 34 项检查：**31 项正常行为 PASS，3 项 BUG_REPRODUCED**。缺陷复现成功不表示功能通过；测试脚本特意区分这两种状态。
5. 核对原生 GPU 资源清单：4 个文件的大小和 SHA-256 均匹配。没有执行 EXE/DLL；匹配仅说明包内一致，不证明二进制安全、GPU 性能或设备兼容性。
6. 核对 Mozilla socket API 的异步关闭约定和 Zotero 文库/key 唯一性约束，避免基于错误宿主假设报告问题。

**未完成：真实 Zotero GUI 安装/启停、真实数据库事务、真实 PDF/MinerU/翻译/嵌入 API 调用、真实 MCP 客户端会话、Wiki 完整流程、GPU 执行、长时间运行与大库压力测试。**

没有把未验证功能算成已失败，也没有把模拟测试冒充真实 Zotero 实测。未修改或重新打包原始插件。

代码位置均指安装包解压后 JavaScript 文件的行号。主脚本为 `content/scripts/zotero-lit-synapse.js`，阅读器脚本为 `mark-reader/content/scripts/zotero-mark-reader.js`。包内 `// src/...` 是构建时的源码模块标记，不代表本次取得了独立 TypeScript 工程。

## 三、已确认缺陷

### B1：旧 socket 的异步关闭回调使新服务被误标为停止，之后停止操作不关闭新监听

**优先级建议：高，正式发布前先修。证据：原始 HttpServer 类模拟复现 + Mozilla API 约定。**

位置：
- 主脚本 `56447–56474`：`stop()` 在 `isRunning` 为 false 时直接返回。
- 主脚本 `56833–56836`：`onStopListening(socket, status)` 无条件将共享 `isRunning` 设为 false，没有判断回调属于哪一个 socket。
- 主脚本 `61031–61056`：`applyServerState()` 在重绑时连续调用 `stop()`、`start(port)`。
- 主脚本 `61034–61040`：禁用服务也依赖 `isServerRunning()` 决定是否调用停止。

执行路径：
1. 旧服务已监听。
2. 修改端口，旧 socket 执行 close。
3. 尚未执行旧关闭回调时，新 socket 已 start，`isRunning=true`。
4. 旧 socket 的 `onStopListening` 到达，错误地把新服务状态设为 false。
5. 再执行 stop，命中早退；新 socket 没有被关闭。

Mozilla 接口文档明确规定 close 会异步触发 onStopListening [1]。因此不是凭空设计的“不可能时序”。测试用确定性队列模拟这一外部约定；没有声称在真实 Zotero 中观察过操作系统端口。

复现输出：
```json
{
  "reportedRunning": false,
  "newSocketStillOpen": true,
  "boundPortReported": null,
  "stopFailedToCloseLiveSocket": true
}
```

影响：状态显示失真，用户认为已停止但新监听仍存活，后续关闭/重启处理不可靠。这里没有证明鉴权被绕过，也没有证明默认会向公网开放；默认 allowRemote 为 false。

最小修复方向：回调按 socket 身份或生命周期编号校验；关闭当前 socket 不应单纯依赖可能过期的布尔值。也可在明确等待旧关闭完成后再启动，但需要统一管理所有重启入口。

真实宿主回归：启动 → 改端口 → 新端口可连接 → 禁用 → 新旧端口都不再接受新连接；再重复启停，并检查状态与端口一致。

### B2：阅读器翻译缓存只用 attachment.key，跨文库相同 key 会共用内存对象和磁盘位置

**优先级建议：中，多文库支持范围内需要修。证据：原始缓存函数模拟复现 + Zotero 数据模式。**

位置：
- 阅读器 `194–200`：缓存目录使用 `attachment.key`，没有 libraryID。
- 阅读器 `553–573`：`translationCaches` 的查找和写入只使用 key。
- 阅读器 `621–639`：写入队列也只使用 key，并写入相同缓存文件。

Zotero 的 items 唯一性约束是 `(libraryID, key)`，不是 key 全局唯一 [2]。不同文库出现相同 key 是数据模型允许的情况。本审查未测量这一情况的现实发生频率，不把它描述为每次使用群组库都会发生。

复现输入：
```text
A: libraryID=1, key=ABCD2345, sourceHash=paper-a
B: libraryID=7, key=ABCD2345, sourceHash=paper-b
```

先加载 A，在 A 中加入手动术语；再加载 B，结果：
```json
{
  "sameDiskDirectory": "/test-data/zotero-lit-synapse/mineru/ABCD2345",
  "sharedInMemoryObject": true,
  "secondPaperSourceHash": "paper-a",
  "secondPaperInheritedGlossary": [{"source":"alpha","target":"A"}]
}
```

已证明的是缓存身份隔离失败、B 取得 A 的缓存对象和术语、两者磁盘路径相同。**没有证明所有译文必然错乱，更没有证明原始 PDF 或 Zotero 主数据库因此损坏。** 段落翻译指纹包含文本等因素，有些情形仍能避免直接复用不匹配的段落结果，不能忽略这一已有保护。

最小修复方向：目录、内存缓存、写入串行队列及关联通知统一采用 libraryID + key；为旧缓存做有归属校验的迁移，不应简单把所有旧缓存归到当前文库。

真实宿主回归：准备两个文库的相同 key 附件，分别保存不同术语和翻译；交替打开、关闭、重启后仍须彼此隔离。

### B3：自动索引期间的普通条目事件被丢弃，群组库不由后续个人库扫描补回

**优先级建议：中，依赖群组库自动更新时必须修。证据：原始注册通知函数和定时扫描函数模拟复现。**

位置：
- 主脚本 `60842–60862`：当 `isAutoIndexing` 为 true 时，通知只进入 MinerU 特殊附件生命周期处理，随后 return。
- 主脚本 `60687–60720`：该处理仅识别特定标题格式的 MinerU Markdown 附件，普通文献不进入自动更新队列。
- 主脚本 `60868–60874`：非忙碌时，普通文献 add 会正常排队；对照测试确认了这一行为。
- 主脚本 `60989–60994`：周期补建只指定 `Zotero.Libraries.userLibraryID`。

复现：
1. 启用自动更新。
2. `isAutoIndexing=true`，表示另一轮自动索引尚未完成。
3. 向文库 7 加入普通文献 GROUP123，发出 add 通知。
4. 队列长度为 0，不是“排队后等候执行”。
5. 解除忙碌，运行周期补建；它只对个人库 1 调用 buildIndex。

输出：
```json
{
  "groupLibraryID": 7,
  "queuedDuringBuild": 0,
  "periodicBuildLibraryIDs": [1],
  "groupChangeNotRecoveredByPeriodicScan": true
}
```

影响：受影响群组文献可能未进入语义/正文索引，直到后续相关事件或手动补建。元数据检索仍可能找到它，不能因此说所有检索都失效。个人库可能被后续个人库扫描补回，不能把群组库结论无条件扩大到全部文库。默认 autoUpdate 为 false；开启该功能后才适用此触发路径。

最小修复方向：忙碌时保留/合并 `(libraryID, itemKey)` 待处理任务，而不是丢弃通知；索引结束后继续排空。确认已有重试队列与新增事件都能保留，不要只修“之前已入队”的任务。

真实宿主回归：在长索引任务进行中向群组库新增/修改文献；任务结束后无需再次编辑这篇文献，仍能自动完成该文献索引。

## 四、通过的检查为什么有意义

31 项通过检查覆盖有限但具体的行为，不是通篇风格检查：

| 检查组 | 结果与边界 |
|---|---|
| HTTP 消息处理 | 中文/emoji UTF-8、Content-Length 等待完整正文、冲突长度拒绝、chunked 解码、分段写出通过 |
| 访问控制 | 默认本地策略下拒绝外部 Origin/Host；开启鉴权后拒绝缺失/错误令牌并接受正确令牌 |
| 服务基础状态 | 首次启动和普通停止通过；故障集中在异步旧回调与重启交错 |
| 搜索分页状态 | 正常续页、查询改变、过期游标、不同工具游标隔离检查通过；不代表排序质量已评估 |
| 阅读器基础缓存 | 正常缓存持久化、文本改变后的指纹变化、正常 chat response 解析通过 |
| MCP 基础协议 | 初始化返回 3.1.0 和所支持协议；坏 JSON、坏 JSON-RPC、未知工具拒绝通过 |
| 写入保护 | 默认不列出写工具，显式调用也被拒绝；用户拒绝时不创建/保存；批准后模拟保存一次 |
| 写入错误传播 | 不存在的目标笔记和空新笔记会返回 isError，而不是伪装成功 |
| 隐私与索引身份 | 显式本地路径字段清理通过；空闲时群组条目按文库身份正常排队 |

安装包默认禁用 MCP 服务、MCP 写入、文件导入、远程访问、GPU 加速和语义自动更新；写入确认默认为开启。上述写入保护测试使用实际默认偏好。Wiki 自动写入另有配置，本次没有把 MCP 写入开关等同于全部 Wiki 存储权限。

这些结果说明存在实际可工作的基础逻辑与保护，支持“可进入受控试用”的判断；不支持“全面安全”“所有集成都稳定”“31/34 等于某个可靠性百分比”。

## 五、停止修改与验收建议

不建议基于本报告展开全项目重构。优先做三处局部修复，并建立对应回归测试。

最低真实宿主验收可以收敛为：
1. 在受支持的 Zotero 9.0.x 安装、启停、重启，验证配置保持。
2. 用少量文献跑通元数据检索、建索引、正文检索、阅读器显示和一次真实翻译；使用 Wiki 时补上该实际工作流。
3. 执行 B1 的端口/关闭回归；支持多文库时执行 B2、B3 回归。
4. 需要写功能时，在测试文库验证拒绝不写、批准正确写、失败不假报成功；未使用的 GPU/远程能力不要宣称已验收。

**当前建议：可以开始受控个人试用；稳定发布暂不通过。修复这些问题并完成声明范围内的真实宿主验收后，就有明确理由完成当前版本，而不是继续以“让 AI 再也找不出建议”为结束条件。**
