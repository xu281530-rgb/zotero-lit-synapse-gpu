# Zotero LitSynapse：第三轮补查与使用门槛

审查日期：2026-09-05  
审查对象：此前上传的 `zotero-lit-synapse(1).xpi`，版本 `3.1.0`。本轮没有收到新的修复包。

## 一、结论

**仅修复上轮的 MinerU 跨文库隔离问题，不足以据此宣布全部功能稳定。** 本轮在原包中补查了写入失败、Markdown 替换、状态持久化及部分 Wiki 文件写入路径，新增确认三个条件性缺陷，集中于两个方面：

- D1：元数据更新中途失败，已经修改的内存对象没有恢复；随后一次仅修改标签的保存可能连带提交这些字段。
- D2a：MinerU 状态文件一次写入失败，会使后续写入队列持续收到同一个旧错误；文件系统恢复后也不自动恢复。
- D2b：MinerU 状态首次并发加载产生两个独立对象，可能丢掉其中一份“不要自动重建 Markdown”的记录。

这三个场景在更早的旧包中也能复现，**不是上一轮修复导致的新回归**。上一轮没有覆盖这些路径，不能把“此前没有发现”理解为“此前已证明这些路径正确”。

可用性建议：
- 单一文库、本地、关闭 MCP 写入、少量已有备份的文献：仍可进行受控试用。本轮新问题不足以否定全部读取与检索能力。
- 开启元数据写入：先修 D1，它影响用户对“操作失败”的理解及实际数据一致性。
- 依赖多文库 MinerU：还需完成上轮 C1。
- 宣称稳定解析与异常恢复：修 D2a；D2b 同属这份状态管理代码，应一并修复并回归。
- 真实 Zotero、实际外部服务和客户端集成验收仍须完成。未实测不是额外的 bug，但也不能列为通过。

## 三、D1：元数据更新失败后留下未恢复的内存修改

### 3.1 触发条件与代码路径

需要用户开启 MCP 写入并批准操作。关闭写入或拒绝确认的对照测试均没有修改。

`content/scripts/zotero-lit-synapse.js`：

- `45291–45293`：请求分发调用 `assertWriteMetadataArgs`。
- `44737` 附近的参数校验检查对象形状与值类型，但没有预先验证所有字段名对目标条目有效。
- `48610–48648`：获取实际条目后，按顺序调用 `getField`/`setField`。后续字段无效时，前面字段已经改变。
- `48674` 附近：只有全部字段及作者处理完成后才调用 `saveTx()`。
- `48685–48692`：捕获异常并返回 `success: false`，未恢复已经改变的对象。
- `48537–48587`：后续 `write_tag` 获取同一条目，再调用 `saveTx()`。

### 3.2 确定性复现

初始标题为 `Original title`。通过 MCP 提交：

```json
{
  "name": "write_metadata",
  "arguments": {
    "itemKey": "PAPER001",
    "fields": {
      "title": "Uncommitted title",
      "notARealField": "bad"
    }
  }
}
```

返回工具错误，第一次请求没有执行保存；但模拟的共享条目对象标题已经变为 `Uncommitted title`。

然后仅请求：

```json
{
  "name": "write_tag",
  "arguments": {
    "action": "add",
    "itemKey": "PAPER001",
    "tags": ["reviewed"]
  }
}
```

原始标签写入逻辑执行一次保存，连带保存了先前“失败”的标题修改。

结果：

```text
元数据调用返回错误：是
第一次调用立即保存到数据库：否
错误后的缓存标题：Uncommitted title
后续调用要求修改标题：否，仅添加标签
后续保存后的标题：Uncommitted title
```

### 3.3 为什么不只是模拟出来的虚构情况

Zotero 官方 `DataObjects.getByLibraryAndKeyAsync` 最终调用 `getAsync`；对象已加载时，`getAsync` 返回内部缓存中的同一对象。官方 `Item.setField` 会修改 `_itemData` 并记录变化，无效字段会抛错。

因此，该测试使用“同一条目对象继续被获取、字段在保存前已改变”的模型有宿主源码依据。**数据库持久化结果仍为模拟验证，应在真实宿主补一条回归。**

### 3.4 严重性与最小修复要求

这是写入模式的数据一致性问题，建议在开放元数据修改前处理。不是所有失败都会立即改数据库，也不是所有用户都会遇到；触发要求是已经有字段修改、后面发生异常，并且随后保存同一对象。

修复应在隔离/暂存对象上完成完整验证，并确保异常时恢复内存对象状态。只增加错误提示，或只把最后的 `saveTx()` 再包一层事务，不能证明已经解决“保存前就发生的部分修改”。

验收：让第二个字段失败，确认失败后读取的标题未变，再执行一次只加标签的保存，确认标题依旧未变。

## 四、D2a：MinerU 状态文件写入队列一次失败后持续失败

### 4.1 根因

主脚本 `4050–4076` 附近：

```javascript
this.attachmentStateWrite = this.attachmentStateWrite.then(async () => {
  // create directory and write state
});
await this.attachmentStateWrite;
```

前一个 Promise 已拒绝时，后面 `.then(successHandler)` 中的写入不会执行。队列没有恢复分支。

### 4.2 基础复现

对第一次状态文件写入注入一次 `SIMULATED_TRANSIENT_IO_ERROR`；之后的文件写入接口已经可以正常成功。

依次执行：
1. 禁止自动恢复附件 A 的 Markdown。
2. 禁止自动恢复附件 B 的 Markdown。
3. 重新允许附件 A 的 Markdown。

后两次仍收到第一次的旧错误；真正的状态文件写入总共只尝试了一次。

这不是“磁盘一直不可写”，而是磁盘接口已经恢复后，插件根本不再尝试。

### 4.3 从真实服务入口观察到的影响

另一个同类测试让 A 的禁止自动恢复记录先遭遇一次写入失败，再对 A 执行：

```javascript
getMarkdownForAttachment(A, {
  force: true,
  allowParse: true,
  userInitiated: true
})
```

原始解析与保存流程获得了合成解析内容，并成功导入 Markdown。但是流程末尾 `allowAutomaticMarkdown` 继承状态写入队列中的旧错误，导致整个解析调用抛错，并写出失败缓存。

```text
实际注入的 I/O 错误次数：1
此后 Markdown 已创建：是
解析接口仍报错误：是
缓存元数据被记录为失败：是
```

涉及主脚本 `4986–5048` 的完成、状态更新及异常处理路径。

### 4.4 建议与边界

这是异常恢复问题，不代表正常磁盘条件下每次解析都会失败。它影响稳定性和报错可信度，适合在稳定版前处理。

写队列必须在前一任务失败后允许下一任务执行，同时将当次错误如实交给调用者；不能靠永久吞掉所有错误来“修好”。另需避免把已经产生有效解析产物、仅辅助状态写入失败的情况混同为整个解析失败。

重建服务或重启应用可以清除这条内存中的拒绝链，但无法自动补回未持久化的状态；这只是临时恢复办法，不是修复。

## 五、D2b：状态首次并发加载导致删除偏好记录丢失

### 5.1 根因

主脚本 `4050–4098`：

`readAttachmentState()` 在缓存为空时进行异步读取；它没有保存“正在初始化的 Promise”。两个请求都可能在首次读取完成前进入，分别取得不同的状态对象。较晚赋给 `this.attachmentState` 的对象覆盖较早对象；后续写入从当前对象取值，丢掉另一个对象上的修改。

### 5.2 服务入口复现

测试使用**同一文库、不同 key** 的两个 PDF，排除了上轮 C1 的跨文库同 key 条件。

先为两个 PDF 各生成正常结构化缓存，随后让它们的 Markdown 子附件均不可见；创建新的 MinerUService，模拟重新打开后的首次读取。并发调用两次：

```javascript
getMarkdownForAttachment(attachment, { allowParse: false })
```

两条请求都进入 `4425–4434` 的“缓存存在但生成附件不在，记录不要自动重建”分支。两次都返回空结果，但最终状态文件只记住第二份文献：

```json
{
  "requestedSuppressions": ["1:SAMEKEY1", "1:OTHERKEY"],
  "persistedSuppressions": ["1:OTHERKEY"]
}
```

对照：串行更新两份记录正常；提前完成一次状态初始化后再并发更新，也能保留两份记录。

### 5.3 影响与修复

已经确认的是**一份抑制自动重建的状态记录丢失**。本测试没有证明它必然立刻重新生成附件，更没有证明原始 PDF 被修改。重新生成还取决于后续缓存是否存在、解析是否被允许等路径。

建议使用共享的首次加载 Promise，让并发调用拿到同一份状态，再有序持久化。这一项优先级低于 D1，但与 D2a 位于同一处状态管理实现，应一并测试。

## 六、本轮得到的正面证据

本轮新增通过的检查包括：

- 合法且获准的元数据请求只执行一次保存。
- 写入关闭、用户拒绝、字段值类型错误时，不发生内存字段变更。
- 标签参数误传字符串时，不会先清空原标签。
- 文件导入开关未打开时，已获批准的写请求仍不能导入文件。
- MinerU 正常首次解析能生成可读的 Markdown 子附件。
- 替换 Markdown 的导入阶段失败时，旧附件保留。
- 新导入 Markdown 内容不可读时，清理新附件并保留旧附件。
- Wiki 阅读笔记的文件写入实际传入同目录临时文件路径，符合其请求原子替换的设计。

最后一条只验证传参及代码路径，不是实测底层文件系统的原子性，也不意味着 Wiki 全流程已验收。

## 七、明确的停止条件

不应以“下一轮 AI 没有新意见”作为结束标准。建议按要发布的功能冻结验收范围：

1. 已知缺陷：上轮 C1，以及本轮适用于声明功能的 D1、D2a、D2b，改为“修复后应成功”的断言并通过；同时保留原正常行为测试。
2. 真实宿主：在安装包声明的 Zotero 9.0.x 环境，完成安装重启、服务启停、实际客户端检索、实际解析和翻译。
3. 数据安全：拒绝确认不写入；无效字段失败后再保存其他属性，不夹带失败请求的变化；替换失败不丢旧附件。
4. 恢复与持久化：并发首次状态读取不漏记录；注入一次临时写入失败后，后续操作可恢复；重启后偏好、缓存及索引状态符合预期。
5. 可选功能：用到多文库、Wiki、文件导入或 GPU 时，验收对应流程；未验收的功能标明范围，不必阻止已验收功能交付。

达到选定范围的验收条件，可以发布并进入常规维护，不必为未知的、没有证据的假设无限重构。当前补查支持“有限范围内受控试用”，不支持“仅修 C1 后全部功能就自动稳定”的承诺。
